## 接下来按以下顺序执行

### 第一步，完成原型走查，同时补齐资产记录

实施模型先阅读本文件、实施记录、盘点报告和原型源码。以现有原型为基础启动预览。

```powershell
Set-Location D:\transport-archive
node scripts/preview-prototype.cjs
```

在本机浏览器访问 `http://127.0.0.1:4179`。若端口已占用，先核对已有服务是否为这个原型，再决定复用或换端口。按下面的业务动作走查，并将预期和实际结果写入 `docs/PROTOTYPE_REVIEW.md`。

|动作|验收结果|
|---|---|
|同一车牌创建两趟|两个独立档案，继续入口不串档|
|自由选择三项基础任务|每项明确显示已收张数和水印状态，未齐全时不能提交|
|第一次开箱拍三张，其中一张首次失败后重试|仍为一次开箱，重试成功后恰好三张，首次拍摄时间不变|
|返回档案再点开箱|新增第二次开箱；进入第一次开箱可以补拍|
|提交基础照片后追加|仍可开箱、关箱和补拍，提交文案容易理解|
|水印生成失败|保留原图、显示失败、可单独重做；查看器准确呈现当前图片类型|
|取消拍摄、刷新、返回原事件|草稿和状态可解释，空操作不显示成已发生事件|
|移除已提交基础任务最后一张成功照片|按原型的先补拍规则提示；有效数量和完成状态一致|
|总部筛选档案并查看第一次开箱第二张|分组、照片顺序、原图切换正确；返回保留查询条件|

工程走查完成后，让司机或负责人以司机身份、总部人员或负责人以总部身份各完成一次关键路径，记录角色、误点及需要解释的位置。测试人员为负责人时如实登记。当前建议自由拍摄顺序、提交后最后一张先补拍再移除，均应在走查记录中确认。

资产工作可同步推进。核对已有恢复产物，整理脱敏摘要；查验平台主体、绑定和体验权限；制定索引与文件恢复验证步骤。平台登录需要扫码时明确给出入口和待核事项。云端绑定核验尚未完成时，本地原型走查仍可继续。

### 第二步，做一张真实照片的技术试件

先明确接口和部署目标，再修改测试环境。读取当前云端配置，核实目标仍为专用测试环境，保存修改前配置和函数快照。云函数运行时、依赖和图片服务参数按照届时官方文档及实际账户核验。

交付一张真实照片从手机到总部的完整证据，包括原文件上传、首次接收时间、设备时间、定位状态、事件归属、水印生成结果、两张图的查看结果及失败重试。记录中文字体、横竖图、小尺寸图、长地址、运单文字、冷启动和处理耗时。天气失败可以继续，天气观测时间无法匹配拍摄时刻时显示不可用。

优先验证服务端生成派生图。其可用性取得证据后，统一页面调用、云函数清单及流程测试。若需采用客户端方案，先写出失败证据及相同矩阵下的验证结果，再更新契约。

原型测试通过不能代替本步骤。模拟图也不能作为手机实拍结果。

### 第三步，重构事件和照片归档

通过技术试件后，按下面四批修改，每批提交变更记录和对应验证。

1. 建档及权限。补服务端车牌校验、唯一档案号、创建幂等和历史空凭据处理。
2. 事件。让一次开箱操作获得稳定事件 ID，之后多图复用；固定事件去重，动态序号并发安全。
3. 照片。稳定照片请求 ID、原图归属校验、独立水印状态、可恢复写入和计数更新，覆盖响应丢失后的重试。
4. 基础提交。服务端核实三项完成、重复提交保持首次时间、提交后继续追加。

核心验收用同一趟测试运输完成两次开箱，第一次三张、一张重试。最终第一次恰好三张，第二次独立，无重复照片。随后更新司机端、总部界面和真实环境用例。
