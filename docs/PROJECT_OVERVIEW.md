# 项目概览（PROJECT_OVERVIEW）

- 项目代号：Transport Photo Archive
- 项目名称：运输过程影像采集与事件归档系统
- 文档版本：V1.0
- 项目性质：真实业务项目 / 微信小程序 + Web 管理后台
- 执行对象：WorkBuddy（AI 项目开发执行者）
- 项目管理与技术审核：ChatGPT

---

## 1. 项目要解决的核心问题（一句话）

运输司机在运输过程中按实际节点拍照，系统自动记录拍摄时间、日期/星期、GPS 定位与天气，为照片生成水印，并把照片按「运输档案 → 运输事件 → 照片」三级关系归档；总部工作人员在后台按档案与事件快速查到某辆车某一次运输的完整影像记录，用于货损、质量争议等场景的责任追溯。

> 本项目**不是**物流管理系统、车辆管理系统、车队管理系统、运输调度系统。所有设计与开发只围绕「影像采集 + 事件归档 + 后台检索」这一核心。

## 2. 核心业务理解（对任务书第三节的确认）

### 2.1 三级父子关系（最重要）

```
TransportRecord（运输档案） 1 ──── N TransportEvent（运输事件） 1 ──── N PhotoRecord（照片）
```

- **一次运输 = 一份运输档案**。同一车牌号进行下一次运输时，必须新建档案，不能合并。
- **一份档案包含多个运输事件**。
- **一个事件可以包含一张或多张照片**。
- **一张照片只属于一个事件，一个事件只属于一份档案**。

### 2.2 事件分类

**固定运输节点（每份档案各一类，通常不重复）：**

| 事件类型 | 中文名称 | 说明 |
| --- | --- | --- |
| WAYBILL | 货运运单 | 本次运输对应运单资料（第一步拍摄） |
| CARGO_PHOTO | 货物照片 | 记录本次运输完整货物外观（第二步） |
| LOADED_COMPARTMENT | 装货完成照片 | 货物装车后实际情况（第三步） |

**动态运输事件（可重复多次）：**

| 事件类型 | 中文名称 | 说明 |
| --- | --- | --- |
| DOOR_OPEN | 开门 | 每次开门新建一个独立事件，序号递增（第1次开门、第2次开门…） |
| DOOR_CLOSE | 关门 | 每次关门新建独立事件，不强制与开门配对 |
| OTHER | 其他 | 可选，特殊情况下留存照片（可备注） |

### 2.3 关键业务规则

1. 事件数量不固定，动态事件可无限重复，不强制开门/关门成对。
2. 事件按实际创建/记录顺序排列。
3. 每张照片必须明确关联档案编号 + 事件 + 文件 + 拍摄时间 + 服务器接收时间 + 定位 + 水印。
4. 照片只有服务器确认保存成功后才显示「上传成功」；失败可重试，且不因重试产生重复事件/照片。
5. 档案提交（状态 → 已提交）后**仍可继续追加**开门/关门事件，使用同一档案编号；后台需能区分初始照片与追加照片。
6. 每份档案生成独立 `access_token`（安全访问令牌），司机通过该令牌进入指定档案，防止多份运输混淆。

## 3. 用户与使用周期

- **第一类用户：运输司机**——微信小程序，填写车牌号 → 创建档案 → 按节点拍照上传。
- **第二类用户：总部工作人员**——电脑浏览器后台，检索档案 → 按事件查看照片 → 查看原图/水印图。
- **第一阶段不设复杂角色体系**（仅司机 + 管理员）。
- **使用周期**：每年约 12 月至次年 5 月农产品运输产季，需长期保存，需考虑持续扩展。
