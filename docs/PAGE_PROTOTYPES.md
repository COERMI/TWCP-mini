# 页面原型（PAGE_PROTOTYPES）

## 2026-11-21 主流程确认版（当前版本）

用户已明确确认：运输前依次拍齐货运单、货物码放、装好的车厢；途中每次开门、关门必拍，问题随时反馈，全部卸货后由人确认完成运输。司机入口只对应本趟，没有历史入口列表或通用新建。详见 `PROTOTYPE_DOOR_FLOW_REVIEW.md`。下文为上一版记录，冲突处以本节及新走查记录为准。


## 2026-11-21 现场流程原型（上一版记录）

依据《司机拍照流程优化建议.md》，用户明确要求“先更新现有原型”。本轮只修改本地原型与其预览、验证和说明，没有修改小程序业务页、云函数或真实邀请能力。

入口仍为 `docs/prototype/index.html`；推荐在项目根目录运行 `node scripts/preview-prototype.cjs`，用本机浏览器访问 `http://127.0.0.1:4179`。不需要安装依赖。

### 本趟入口

- 总部新增“准备本趟拍照”：车牌、发货日期、给司机看的装货地/方向、可选批次。
- 生成本浏览器内的独立演示邀请；司机看车牌和本趟说明，点“车牌对，开始拍照”。
- 邀请 URL 固定关联档案。重复打开、刷新和打开旧入口都不创建新趟；进入后优先显示本趟待传/待处理照片。
- 演示邀请绑定指定演示身份；转给另一演示身份会提示联系负责人，需通过专门接续邀请继续。记录新照片的上传操作者，不改写原照片归属。
- 没有专属入口时保留通用备用入口；换新货先展示上一趟日期、车牌及照片数并确认。原趟队列保持归属。
- 这不是微信分享实现，不是真实身份认证，不发送微信消息；正式邀请的校验、领取、转发限制和接续授权都需服务端实现。

### 司机三个现场入口

1. **装货拍照**：装货前空厢和预冷温度可独立进入，不受运单是否已取得影响；三项基础仍保留“运单→货物→车厢依次解锁”；装货后补封车/车牌和装后温度。
2. **卸货拍照**：每次卸货单独一组，包含开门前车门、温度仪表、开门后货物、环境、过程、卸后车厢和签收单。中途提示拍剩余货物，最后一站才拍空厢。不要求提前填写完整路线。
3. **有问题拍照**：全景与近景提示，另存问题现场，可进入旧组补拍。

现场按单个任务展示短提示和示意图；拍照→看清了吗→用这张→下一项。再拍一张留在同一项目/现场。队列照片在首次使用时绑定记录、现场、事件、照片 ID 和上传者；切换到新趟后仍从原趟补传。

未取得的单据可以稍后补。错过的现场可记“当时未拍”，后续照片保留实际采集时间，历史缺项不会因补拍被抹掉。原型不校验图片内容，资料已收不代表质量合格。

### 送完与资料分开

- 每次卸货结束询问“还有下一站 / 没有，全部送完 / 先不确定”。
- 没有下一站须再确认；记录确认人和时间后，仍展示未传照片及缺项，优先展示签收单，不把“货送完”误写为“资料齐全”。
- “还要继续送”可纠正，必须选择原因并保留旧确认记录；不能靠日期、照片齐全、一次关门或签收单推断整趟结束。
- 总部可在填写原因并确认后，演示代确认或纠正。司机端会区分“负责人代确认”和拍摄者本人确认。
- “基础已提交”和最后一张基础照片先补拍成功再移除的规则保留；软删除新增原因、操作者与时间。

### 辅助与总部查看

- 大字提示、听提示、静音、联系负责人入口。语音本轮使用浏览器朗读演示，未制作预录中文或方言音频；联系按钮只说明从原微信会话联系，不拨号、不发消息。
- 总部按实际现场分组，分开显示送货确认、缺项、照片数、准备时间、首次拍照时间。发车时间没有来源时留空，不推断。
- 同一次现场的不同拍摄项目可以连续翻图，原图/水印示例保留相同照片 ID；可查看确认、纠正、接续邀请及上传者。
- 旧版动态事件保留原分组，不按时间猜测合并。

工程走查和范围边界见 `PROTOTYPE_WORKFLOW_REVIEW.md`。真实相机、定位、云存储、水印、微信分享、权限和真实人员无提示走查均未通过本轮原型验证。

## 2026-11-21 基础版原型（上一版留档）

入口：`docs/prototype/index.html`。本地预览：在项目根目录执行 `node scripts/preview-prototype.cjs`，访问 `http://127.0.0.1:4179`。不需要安装依赖，也可以直接打开 HTML。

这是流程原型，使用浏览器内示例数据，不调用相机、定位、云函数或数据库。不将原型演示成功写成真机或云归档验收通过。首屏提供同牌的空档案和多事件档案；两端共享当前浏览器的演示数据。

### 已由负责人确认的规则

- 基础任务保留旧规则：**运单 → 货物 → 车厢依次解锁**，不是审查方案建议的自由选择。上一类至少有一张已归档照片才解锁下一类；开箱和关箱独立可拍，不要求配对。
- 基础照片提交后，**移除某类最后一张已归档照片之前，必须先补拍并归档成功**。
- 以上两项由本聊天的结构化问答直接确认，覆盖原审查方案中的待确认建议。

### 司机端

1. 首页：明确区分“继续这趟运输”和“开始新的一趟”，同一车牌可新建独立编号，最近档案按 ID 分开保留。
2. 本趟：显示基础 0/3—3/3 和锁定原因；按钮为“提交基础照片”。提交后提示仍可开箱、关箱、补拍。
3. 事件页：“拍第一张 / 拍下一张”复用当前事件。点本趟的“开箱拍照”创建新事件，点时间线的旧事件只进入补拍。空事件退出不计次数。
4. 确认页：示例预览、首次采集时间、“重拍 / 使用这张”。返回时确认放弃尚未使用的照片。复选框可模拟弱网上传失败和水印失败，正式司机端不提供这些工程选项。
5. 照片状态：正在上传原图 → 原图已收、水印处理中 → 已归档；失败重试复用照片 ID 和首次时间。水印失败可看原图、单独重做，水印未就绪不能点击“水印图”。
6. 已归档照片移除经过确认，原型仅软删除并重算有效张数。已提交基础资料的最后一张归档照片受保护。
7. 刷新可恢复已确认的演示照片；被中断的模拟上传转为可重试状态。尚未确认的拍摄预览不会假装已经上传。

### 总部端

- 列表显示同牌独立档案、北京时间日期及状态筛选、有效事件数和照片数；进入详情再返回保留筛选与页码。
- 基础组按运单、货物、车厢排序；途中事件按时间及稳定 ID 排序。空档案与无查询结果分别提示。
- 同事件连续翻图，原图和示例水印图使用同一底片与同一照片请求 ID；水印失败时只展示原图入口。
- 展示首次时间、原图收到时间、坐标系与精度；天气示例明确为“不可用”，不冒充历史观测。

### 验证

工程浏览器走查见 `PROTOTYPE_REVIEW.md`。负责人已确认两项业务规则；真实司机无口头帮助走查、总部人员走查仍需记录。正式相机、定位授权、私有文件访问及水印输出将在后续试件验证。

## 一、司机端（微信小程序）

### 1. 首页（填车牌）—— 参考原型图「driver_home_page」

- 标题：运输照片采集
- 副标题：请填写本次运输的车辆信息
- 车牌号码输入框（非空 + 宽松格式校验，兼容新能源绿牌等）
- 大按钮「开始记录运输」
- 点击后：生成唯一档案编号（如 TR2026120001）→ 状态=进行中 → 生成 access_token → 跳转采集页

### 2. 采集页（严格引导）—— 参考原型图「guided_photo_flow」

- 顶部：档案编号 + 车牌号 + 进度「第 X 步 / 共 3 步」
- 固定节点（**严格顺序锁定**，上一步未拍完下一步不可点，可返回补拍）：
  - 第1步 货运运单
  - 第2步 货物照片
  - 第3步 装货完成照片
- 途中事件（独立大按钮，随时可拍、不限次数、不强制配对）：
  - 开门照片 / 关门照片
- 底部：已拍统计 + 「完成本次运输」按钮
- 每个事件可填可选备注

### 3. 拍照上传流程

```
点拍照按钮 → 调用摄像头 → 拍摄 → 预览（可删除/重拍）
→ 获取时间 + 定位 + 天气 → 上传原图 → 服务器生成水印图
→ 保存档案/事件/照片关联 → 显示「上传成功」
```

- 上传失败：提示 + 可重试，不把失败显示为成功，防重复提交（幂等）
- 弱网：显示上传进度与待上传状态

## 二、总部端（Web 管理后台，Vue3 + Element Plus）

### 4. 登录页

- 账号 + 密码输入，登录/退出；未登录不可访问；账号不硬编码在前端

### 5. 档案列表页（首页）

- 表格列：档案编号 / 车牌号 / 创建时间 / 最近更新 / 照片数 / 事件数 / 状态 / 操作(查看详情)
- 搜索筛选：按车牌号、档案编号、创建日期、状态

### 6. 档案详情页 —— 参考原型图「admin_record_detail」

- 顶部：面包屑 + 退出登录
- 基本信息区：档案编号 / 车牌 / 创建时间 / 最近更新 / 状态 / 照片数 / 事件数
- 左侧「运输事件列表」：按创建顺序（固定节点 + 第N次开门/关门），点击切换
- 右侧「事件照片详情」：缩略图 + 拍摄时间 + 服务器接收时间 + 定位 + 天气 + 车牌/档案/事件；可看大图、查看原图
- 默认显示水印图，原图需登录查看（防外泄）；追加照片用「追加」标记区分

## 三、页面流转关系

```
司机端：首页(填车牌) → 采集页(严格引导) → 完成提交 ⇄ 提交后追加
后台：  登录 → 档案列表 → 档案详情(事件列表 + 照片详情)
```
